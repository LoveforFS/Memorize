## 三、关键技术点

### 3.1 三层依赖方向

```
View（GameView/CardView/Cardify/Pie/AspectVGrid/ThemeButton/AnimationTiming）
        │ 只读 @Published、只发用户意图
        ▼
ViewModel（GameViewModel + MismatchTimerScheduling + GameAnimationCoordinator + CountdownClock）
        │ 唯一状态源：同步模型状态、调度时序、判定动画边界
        ▼
Model（Theme / Card / Game）
        纯规则：牌组、翻面、配对、计分、重开、切题
```

禁止反向引用：模型不 import SwiftUI，视图不直接改模型。这样模型可以脱离界面做单元测试，
计时器可以注入假实现，几何计算可以纯函数验证。

### 3.2 状态单一来源与同步

`Game` 持有牌组与得分，`GameViewModel` 只在 `choose/newGame/chooseTheme/flipBack` 后调用
`syncFromGame()` 把 `game.cards`、`game.score` 写进 `@Published`。视图不保存牌局副本，
因此不存在“视图与模型各算一次”的一致性问题。

### 3.3 错配时序与令牌失效

- 错配后 `isInteractionLocked = true`，`scheduleFlipBack()` 用 `pendingTimerToken: UUID?` 登记本次任务；
- 延时回调里先校验 `pendingTimerToken == token`，令牌不匹配说明牌局已重开或切题，回调直接丢弃；
- `newGame()` / `chooseTheme()` 会先把令牌置空，避免旧回调翻回新牌局。

这是“过期异步回调”的通用处理范式：**异步任务必须带可作废的令牌**。

### 3.4 动画边界：版本号而非布尔开关

`GameAnimationCoordinator`：

- `beginFlip(for:)`：同一张卡片在动画未结束时拒绝重复播放（`Set<UUID>` 去重）；
- `scoreDidChange(from:to:)`：数值未变返回 `nil`，视图不播动画；变化才递增 `scoreRevision`；
- `beginNewBoard()`：清空进行中的翻牌并递增 `boardRevision`，视图据此重播错峰发牌。

视图只订阅版本号，不判断“该不该动画”，从而避免快速连点、动画中途切题造成的叠加与闪烁。

### 3.5 倒计时四态状态机

`CountdownState`: `idle → running ⇄ paused → finished`。

| 行为 | 前置条件 | 结果 |
| --- | --- | --- |
| `startCountdown(duration:)` | `duration > 0` | 停止旧计时，重置剩余与总时长，`didTimeOut = false`，进入 `running` |
| `startCountdownIfNeeded()` | `state == .idle && countdownDuration == 0` | 幂等启动，`onAppear` 重复调用不会重开 |
| `tickCountdown()` | `state == .running` | 剩余减一；归零进入 `finishCountdown()` |
| `pauseCountdown()` | `state == .running` | 停表并保留剩余 |
| `resumeCountdown()` | `state == .paused` | 从剩余继续 |
| `finishCountdown()` | 剩余归零 | 停表、剩余 0、`didTimeOut = true`、锁定交互 |
| `completeMismatchFlipBack()` | 有挂起错配 | 翻回后按 `countdownState == .finished` 决定是否解锁 |

难点：超时锁不能被错配翻回任务意外解除，所以解锁条件写成“是否处于结束状态”，
而不是简单置 `false`。

### 3.6 纯函数几何：Pie 与 Cardify

- `PieGeometry.progress(remaining:total:)`：`total <= 0` 返回 0，`remaining <= 0` 返回 0，
  `remaining >= total` 返回 1，其余按比例；
- `PieGeometry.endAngle(for:)`：进度先裁剪到 0…1，再从 -90°（12 点方向）顺时针 `360° × progress`；
- `PieGeometry.ringWidth(for:)`：直径 10%，限制 3…10 pt；
- `CardStyle`：宽高比 2:3；圆角短边 12%（6…20）；描边 1%（1…3）；内边距 8%（2…8）；阴影 3%（1…6）。

把这些数值放进 `enum` 的静态方法，既集中了设计规范，也让 8 + 10 条几何用例可以在无渲染环境下验证。

### 3.7 自适应布局算法（AspectVGrid）

从 1 列开始逐列增加，计算 `行数 × 单元高度` 是否不超过可用高度；列数超过卡片数仍放不下时，
按宽高两个方向压缩取更小值。宽度向下取整避免浮点溢出；宽度算到 0 时不渲染 `LazyVGrid`
（`if itemWidth > 0`），避免 `GridItem(.adaptive(minimum: 0))` 造成布局异常。

## 四、重点与难点

1. **异步与状态的竞争**：错配 0.8 秒翻回是异步回调，必须用令牌作废；否则重开/切题后旧回调会污染新牌局。
2. **动画与交互的竞争**：用版本号 + 去重集合约束动画，而不是在视图里加 `if` 判断。
3. **超时锁的唯一出口**：超时后只能通过“再来一局”恢复，翻回任务不得解锁；通关与超时共用同一个结算弹窗。
4. **视图层守卫容易被忽略**：`AspectVGrid` 在极小空间下宽度为 0，必须有渲染守卫；
   可访问性值也应对“未选中”给出明确文案，而不是空字符串。
5. **洗牌带来的测试脆弱性**：重开后按固定下标选卡可能选到同一 emoji，导致错配用例偶发失败；
   正确做法是按 `content` 显式挑选不同卡片。
6. **等价测试的表述纪律**：文档必须标注“原生 / 等价”，不得把 Python 结果写成 `xcodebuild` 通过。

## 六、自我检测（12 题）

1. **三层依赖方向是什么？** View → ViewModel → Model，禁止反向；模型不引用 SwiftUI。
2. **为什么 ViewModel 要调用 `syncFromGame()`？** 让 `Game` 成为唯一状态来源，把模型状态同步到 `@Published` 触发刷新。
3. **错配翻回的令牌机制解决什么问题？** 重开 / 切题后旧延时回调到达时令牌不匹配，直接丢弃，避免翻回新牌局。
4. **同一张卡片连点两次会播两次翻牌动画吗？** 不会：第二次 `isFaceUp` 已为 true，不登记；且 `beginFlip` 对进行中的同一 id 返回 false。
5. **得分没变化时会播动画吗？** 不会，`scoreDidChange` 返回 `nil`。
6. **倒计时状态有哪四个？** `idle / running / paused / finished`。
7. **`startCountdownIfNeeded()` 为什么要判 `countdownDuration == 0`？** 保证 `onAppear` 重复触发不重开倒计时。
8. **超时后为什么点卡片没反应？** `finishCountdown()` 置 `isInteractionLocked = true`，`choose` 前置守卫直接返回。
9. **超时锁如何解除？** 只通过结算弹窗“再来一局”调用 `newGame()`。
10. **`completeMismatchFlipBack()` 的解锁条件为什么不是直接置 false？** 超时状态下必须保持锁定，故按 `countdownState == .finished` 判定。
11. **`PieGeometry.progress` 的边界返回值？** `total <= 0` 或 `remaining <= 0` → 0；`remaining >= total` → 1。
12. **Windows 132/132 能证明 iOS 原生测试通过吗？** 不能；只是业务逻辑等价与状态投影级等价，原生结论需 macOS `xcodebuild test`。
