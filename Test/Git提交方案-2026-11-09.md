# Git 提交方案（P1-2，待授权执行）

> 现状：工作区有 29 个已跟踪文件被修改 + 8 项未跟踪。本次**未执行任何 git commit**，原因见第一节。
> 目的：把"一次性提交全部"拆成 3 个语义清晰的提交，且不把大体积产物入库。

## 一、为什么不直接提交

1. **变更来源不明**：`day5`–`day8` 的 `AspectVGrid.swift`、`ThemeButton.swift`、`MismatchTimerTests.swift`、`run_tests.py`、三份日报 docx 的改动，都在本次接手之前就已存在于工作区，属历史遗留。提示词第 2 节把"Git 未提交"记为既有状态、第 10 节禁止改历史日报。我不清楚这些改动"为何改"，若合成一个提交，提交信息只能写"改了什么"，违反"提交信息需说明为何改"的要求。
2. **混合打包会丢失可回溯性**：把 D5–D7 的历史修补与 D8 的新增工程文件（`Memorize.xcodeproj/`）、5 份新文档放进同一提交，日后无法单独回滚。
3. **验收口径风险**：当前 `check_project.py` 的 WARN 就是"Git 未提交"；提交后 WARN 会降为 1 条（D4/D5 同日），这属于正常变化，但必须在提交后重跑确认，不能凭推测声称。

## 二、建议的三段式提交（确认后我可逐条执行）

实测差异规模（`git diff --stat day5..day8`）：26 个文件、+232 / −112 行；其中源码类 15 处、`test_results.json` 6 处、日报 docx 3 份、文档 4 份。源码改动集中在 `AspectVGrid.swift`（18 行/处）、`ThemeButton.swift`（2 行/处）、`MismatchTimerTests.swift`（17–18 行/处），与 D5–D8 各目录同步一致，符合"历史副本逐日同步"的特征。

### 提交 1：历史修补（先确认归属）


先前确认：`git diff --stat day5 day6 day7` 只含上述两类文件时再执行；若含日报 docx 改动，**跳过本提交**，交你判断。

## 三、提交前必查（3 条）

```bash
git status --short                      # 确认暂存范围与预期一致
git diff --cached --stat                # 确认无 .xcresult/.mp4/大文件
git diff --cached --numstat | awk '$1>800 {print "大改动："$3}'   # 单文件超 800 行需人工确认
```

## 四、提交后回归

```bash
python day8/WinTestHarness/run_tests.py   # 期望 132/132
python Test/check_project.py              # 期望 PASS=25 WARN=1 FAIL=0（Git WARN 消失）
```

若 WARN 变为 1，说明提交生效；若仍为 2，检查是否漏提交 `day8/WinTestHarness/test_results.json` 等结果文件。
